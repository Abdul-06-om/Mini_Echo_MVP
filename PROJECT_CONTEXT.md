# Mini ECHO — Project Context

Read this file first in any new session. It reflects the actual current state of the
code, not the plan — for the original MVP plan/spec, see `PROJECT.md` and
`docs/superpowers/plans/`. This project is a learning project (the user is new to
software/AI engineering) that has grown past its original 7-step text-only MVP into a
live-avatar product with real third-party integrations. Treat every claim below as
verified against the code as of the last commit on `main`.

## What this is

A local web app: the user chats with an AI doctor persona — Dr. Sarah Chen
(General Practitioner), Dr. Marcus Reyes (Cardiologist), or Dr. Priya Nair
(Oncologist) — in a browser. The reply is generated by AWS Bedrock, spoken aloud by
ElevenLabs text-to-speech, and lip-synced by a real-time Simli video avatar rendered
live in the page — not a static image, not a canned animation.

Backend: **FastAPI**, run via **uvicorn**, Python 3, venv-managed. Frontend: plain
HTML/CSS/JS (no framework) for the page itself, plus one small bundled JS module
(the avatar component) built with **esbuild** because Simli's official SDK requires
npm/ESM and cannot be loaded via a plain `<script>` tag or CDN import.

## Backend structure (`app/main.py`)

Routes:
- `GET /health` — liveness check
- `GET /` — serves `static/index.html`
- `POST /chat` — body `{"messages": [...], "session": {...} | None}` (full
  conversation each call — backend is stateless), returns `{"reply": str}`.
  `session` is optional — see "Roleplay Sessions" below — and may carry an
  optional `reference_material` string (see "Therapeutic Area / Product
  Knowledge" below). Calls `app.bedrock.get_reply`.
- `POST /avatar/session` — body `{"face_id": str | None}`, calls
  `avatar_provider.create_session()` (currently `SimliAvatarProvider`),
  returns Simli's session token JSON as-is. `face_id` is optional and
  defaults to the existing hardcoded Simli face constant when omitted —
  see the Simli integration section below. This is what lets the browser
  start a Simli WebRTC session without ever seeing the API key.
- `GET /voices` — calls `app.tts.list_voices()`, returns `[{"voice_id", "name"}, ...]`
- `POST /tts` — body `{"text": str, "voice_id": str | None}`, returns raw
  `audio/pcm` bytes (16-bit PCM, 16kHz, mono) from ElevenLabs.
- `GET /personas` — returns `[{"id", "name", "role_title", "category",
  "voice_id", "face_id"}, ...]` from the `app.personas` registry (via
  `list_personas()`). Unlike the routes above, this has no try/except —
  there's no real failure mode for a static in-process registry.

Every route that calls a genuine upstream provider wraps that call in
`try/except Exception`, logs the real exception server-side via
`logger.exception(...)`, and returns a generic 503 with a fixed message — no
upstream (AWS/Simli/ElevenLabs) exception text ever reaches the client. This
is deliberate and tested (`tests/test_main.py` asserts the raw exception
message is absent from the response body for each such route). `/chat` also
returns a 400 (not 503) if `session.persona_id` doesn't match a registered
persona — a client error, not an upstream failure.

`app.mount("/static", StaticFiles(directory="static"), ...)` serves `static/` as-is,
including the avatar photo and the built JS bundle.

## AWS Bedrock integration (`app/bedrock.py`)

- Model: `us.anthropic.claude-haiku-4-5-20251001-v1:0` (an inference-profile ID —
  the plain model ID does not work for this model; region `us-east-1`).
- `DEFAULT_SYSTEM_PROMPT` (renamed from `SYSTEM_PROMPT`, value unchanged) is the
  "Dr. Sarah Chen" persona prompt (warm GP, roleplay framing, told not to give
  real diagnoses, told to redirect real emergencies to real emergency
  services) — used whenever no roleplay session is active. When one is,
  `build_system_prompt(persona, session)` composes a dynamic prompt instead —
  see "Roleplay Sessions" below.
- `build_request_body(messages, persona=None, session=None) -> dict` /
  `extract_reply_text(response_body) -> dict` are pure functions, unit tested
  without any network call.
- `get_reply(messages, persona=None, session=None) -> str` makes the real
  `bedrock-runtime.invoke_model` call. `_client` (the boto3 client) is
  constructed once at module import time.
- Credentials come from the standard AWS CLI credential chain (`~/.aws/credentials`,
  set up via `aws configure` for an IAM user named `mini-echo-dev`) — never from
  `.env`, never touched by application code directly.
- **Known account-level constraint**: this AWS account sits inside an AWS
  Organization with a Service Control Policy that explicitly denies Amazon Polly,
  and the user cannot access the Organizations console to change it (this is why
  ElevenLabs is used for TTS instead of Polly — see below). Bedrock itself is not
  affected. Don't assume other AWS services are unrestricted without checking.

## Simli live avatar integration

**Backend** (`app/avatar_simli.py`): `SimliAvatarProvider.create_session()` POSTs to
`https://api.simli.ai/compose/token` with `faceId`, `handleSilence`,
`maxSessionLength`, `maxIdleTime`, and header `x-simli-api-key`, and returns the
JSON response (`{"session_token": "..."}`) unchanged. `FACE_ID` is Simli's own
preset **"Doctor"** face (`f0ba4efe-7946-45de-9955-c04a04c367b9`) — not a custom
avatar, no image/likeness was uploaded.

`create_session(face_id: str | None = None)` accepts an optional
per-request face override, defaulting to `FACE_ID` when omitted.
`POST /avatar/session` exposes this as an optional `face_id` field on its
request body. No caller sends a non-default value yet — the frontend's
`avatar.connect()` still fires once at page load, before any persona is
selected, exactly as before this field existed.

**Frontend** (`avatar-src/doctor-avatar.js`, exported as `DoctorAvatar`, exposed on
`window.MiniEchoAvatar.DoctorAvatar` via the esbuild IIFE bundle):
- Constructor takes `{ videoEl, audioEl, panelEl, stateEl }` — real `<video>` and
  `<audio>` DOM elements, plus any two elements for state (`panelEl.dataset.state`
  is set; `stateEl.textContent` is set to the raw state word).
- `connect()`: fetches `/avatar/session`, constructs a `SimliClient` from the
  `simli-client` npm package using **`transport_mode: "livekit"`** (not `"p2p"` —
  p2p requires ICE servers we don't fetch; livekit mode needs none), registers
  listeners for every `SimliClientEvents` key (`start`, `stop`, `speaking`,
  `silent`, `error`, `startup_error`, `ack`, `connection_info`, `video_info`,
  `unknown`), then calls `client.start()`.
- `think()`: sets state to `"thinking"` (called by the page right before sending
  the user's message to `/chat`).
- `speak(text, voiceId)`: fetches `/tts` for that exact text/voice, then calls
  `client.sendAudioData(new Uint8Array(arrayBuffer))` — the **entire** PCM16 buffer
  in one call, no chunking needed (confirmed by reading `simli-client`'s actual
  source; `sendAudioData` just forwards the whole array over an open WebSocket).
- States actually emitted by this component, and only these five:
  `"connecting"`, `"idle"`, `"thinking"`, `"speaking"`, `"error"`. A sixth state,
  `"listening"`, is added by the Live Voice Conversation feature (see below) but
  is not emitted by `DoctorAvatar` itself — it is set directly on the page's
  `#avatar-panel` element by the voice controller.
- `speaking`/`silent` (SDK events, driven by Simli's own server-side detection of
  the audio we send it) drive the speaking/idle transitions — not a timer, not a
  guess.

## Live Voice Conversation integration

Alongside typed Text Chat, the page now supports a voice-first mode: the
user speaks, the browser transcribes it, and the transcript is sent through
the *same* `/chat` → Bedrock → `/tts` → Simli pipeline Text Chat already
uses — no new backend route exists or was needed.

**STT provider** (`static/stt-web-speech.js`, `window.MiniEchoSTT.WebSpeechSTT`):
wraps the browser's native `SpeechRecognition`/`webkitSpeechRecognition` API
(`continuous: false`, `interimResults: false` — one utterance per listening
turn). Desktop Chrome only; Safari and Firefox lack this API, so the mic
toggle button renders `disabled` with an explanatory tooltip there and Text
Chat is unaffected. Deliberately not run through esbuild — it's a native
browser global, no npm package involved, so the build step stays scoped to
`avatar-src/doctor-avatar.js` as before. Requires no new API key, account, or
AWS permission. Kept behind a 3-callback interface
(`onFinalResult`/`onError`/`onListeningChange`) plus `start()`/`stop()`
specifically so a future cloud STT provider can be swapped in by writing one
new file with the same shape and changing one instantiation line in
`static/index.html` — mirroring the existing `avatar_provider.py` /
`app/tts.py` isolation pattern.

**New `listening` state**: a 6th avatar state alongside the original five
(`connecting, idle, thinking, speaking, error`). Unlike those five, it is
set directly on `#avatar-panel`'s `data-state` (and mirrored onto
`#avatar-state-badge`'s text) by the page's voice controller in
`static/index.html`, not by `DoctorAvatar` — `avatar-src/doctor-avatar.js`
was not modified and has no awareness voice mode exists.

**Turn-taking loop**: clicking the mic button (`#voice-toggle-btn`) starts
listening only while the avatar is `idle`. A `MutationObserver` on
`#avatar-panel`'s `data-state` attribute restarts listening every time the
avatar returns to `idle` after speaking (the existing `"silent"` SDK event,
observed indirectly), forming
`listening -> thinking -> speaking -> listening` automatically until the
button is toggled off. A "no-speech" recognition error just restarts
listening rather than stopping voice mode; other errors (e.g. mic permission
denied) stop voice mode and show an inline error bubble, the same visual
pattern Text Chat already uses for failed `/chat` calls.

**Preventing Sarah's voice from being captured by the mic**: purely a
scheduling guarantee, not audio processing. The recognizer is only ever
started while state is `idle`, and `sendToSarah()` — the single function
both Text Chat and voice mode call — unconditionally stops any active
recognition as its first action, before `avatar.think()`/`avatar.speak()`
run. This covers both the voice-triggered turn and the edge case of a typed
message being sent while the mic happens to be listening.

**Shared conversation history**: no backend or data-model change. Text Chat
and Live Voice both call `sendToSarah(message)`, which pushes into the same
top-level `conversation` array and appends to the same `#chat` log
regardless of which mode produced the message — the two modes were never
separate conversations to reconcile.

See `docs/superpowers/specs/2026-09-17-live-voice-conversation-design.md`
for the full design rationale and rejected alternatives.

**Manually verified end-to-end in Chrome by the user** (2026-09-17), across
multiple consecutive turns: microphone input is captured, speech is
transcribed correctly, the transcribed text appears in the shared
conversation alongside typed messages, Sarah's Bedrock reply is correct,
ElevenLabs audio plays, Simli video and lip-sync work, and the
`listening → thinking → speaking → listening` loop repeats correctly turn
after turn. This is a confirmed working feature, not an unverified one —
treat it as part of the stable baseline the same as the rest of this
document, not as "implemented but unconfirmed."

## Roleplay Sessions

A user can configure a structured roleplay before chatting: HCP persona,
scenario, conversation objective, persona mood/behavior, and difficulty
(easy/medium/hard), plus optional pasted reference material (see
"Therapeutic Area / Product Knowledge" below). Once started, this becomes dynamic system-prompt
context for the *same* Bedrock conversation Text Chat and Live Voice
already share — no new conversation pipeline, no backend persistence.

**Persona registry** (`app/personas/`, a Persona Library — `models.py`'s
`Persona` dataclass + `registry.py`'s `get_persona(id)`/`list_personas()`):
a `Persona` is `{id, name, role_title, category, base_description,
safety_framing, voice_id, face_id}`. Every caller (`app/main.py`) goes
through `get_persona`/`list_personas` — never a raw dict — so moving the
registry to a database later only means rewriting the inside of
`registry.py`; no caller changes. `voice_id` is used to default the
Roleplay setup form's voice selector (still user-overridable); `face_id`
is modeled and accepted by `POST /avatar/session` at the API level, but
every persona currently points at the same verified Simli face — see
"Known issues / open items" for why. Three personas are registered today — Dr. Sarah Chen (General
Practitioner), Dr. Marcus Reyes (Cardiologist), and Dr. Priya Nair
(Oncologist), all under `category="doctor"` — added by the same
one-dict-entry mechanism this paragraph describes, with no change to
`get_persona`/`list_personas`'s signatures or any caller.

**Dynamic system prompt** (`app/bedrock.py`): `build_system_prompt(persona,
session)` composes persona + scenario + objective + mood + a
difficulty-specific instruction (from `DIFFICULTY_INSTRUCTIONS`) into the
prompt Bedrock receives. Called with `persona=None, session=None`, it
returns `DEFAULT_SYSTEM_PROMPT` — today's original hardcoded prompt,
unchanged — which is what keeps `/chat` backward compatible: a request
that omits `session` behaves exactly as it did before this feature
existed.

**Session model**: held client-side only, exactly like the existing
`conversation` array — no session ID, no server-side store, per this
project's stateless-backend decision. `POST /chat`'s `session` field is
optional; the frontend sends it once a roleplay has been started via the
new setup form. `GET /personas` lists available personas for that form's
picker, mirroring `GET /voices`'s existing shape/pattern.

**Shared across Text Chat and Live Voice**: both already call the one
`sendToSarah(message)` pipeline (see "Live Voice Conversation
integration" above); that function includes the active `roleplaySession`
in every `/chat` call, so neither mode needed its own roleplay wiring.
Starting a new roleplay (the "New Roleplay" button) resets both the
session and the conversation array together — a persona swap mid-
transcript wouldn't be a coherent conversation.

**Extensibility, deliberately not built at this milestone**: scoring,
compliance detection, document/RAG grounding, and Admin persona
management were all out of scope here. (Since then, qualitative scoring —
"Performance Feedback" — and a narrow, pasted-text form of grounding —
"Therapeutic Area / Product Knowledge" — have been added the way this
paragraph predicted; compliance detection, RAG/document ingestion, and
Admin remain out of scope.) Because `objective`/`difficulty`/
`scenario` are structured fields (not buried in prompt text), and personas
are already a separate typed registry from sessions, each of those can
attach later — a new endpoint or a new parameter to `build_system_prompt`
— without reworking how sessions flow through the app. See
`docs/superpowers/specs/2026-09-17-roleplay-sessions-design.md` for the
full rationale.

**Manually verified end-to-end in Chrome by the user** (2026-09-17):
Start Roleplay setup (persona, scenario, objective, mood, difficulty) all
work; Text Chat inside an active roleplay gets Bedrock replies that
reflect the configured scenario/objective/mood/difficulty, not the old
generic persona; ElevenLabs audio and Simli video/lip-sync both work
inside a roleplay; Live Voice's full `listening → thinking → speaking →
listening` loop works inside a roleplay across multiple consecutive voice
turns, without Sarah's own speech being picked back up as the user's next
turn; and the pre-existing Text Chat and Live Voice functionality outside
of Roleplay Sessions continues to work unchanged. This is a confirmed
working feature, not an unverified one — treat it as part of the stable
baseline the same as the rest of this document.

## Performance Feedback

After a Roleplay Session completes, the user can request a qualitative
evaluation of their conversation across four dimensions — message accuracy,
objection handling, rapport building, and compliance adherence — plus an
overall summary and specific improvement recommendations. No numeric scores
anywhere (deliberately excluded per source-grounding rationale in the design
spec below); everything is plain-text qualitative feedback. (One narrow
exception, only when Reference Material is supplied: the evaluator may
quote figures that appear in that material — never scores, weights,
thresholds, rankings, or invented numbers. See "Therapeutic Area / Product
Knowledge" below.)

**Backend** (`app/evaluation.py`): four pure functions called by the new
`POST /evaluate` route:
- `build_evaluation_prompt(persona, session) -> str`: composes a system
  prompt telling Bedrock to evaluate only the user's turns (not the persona's)
  against the configured scenario/objective, and to return exactly the six
  required fields as a JSON object with no numeric scoring anywhere (when
  Reference Material is present, figures quoted from it are allowed — see
  "Therapeutic Area / Product Knowledge" below).
- `build_evaluation_request_body(messages, persona, session) -> dict`:
  constructs the Bedrock request body. **Critical detail**: appends a synthetic
  trailing `{"role": "user", "content": "Now produce the evaluation JSON
  object described above."}` message to the transcript *before sending it to
  Bedrock*. This exists because the Anthropic Messages API treats a request
  ending in an `assistant`-role message as a "prefill" (continuing that
  message) rather than a fresh turn — since the roleplay transcript naturally
  ends in the persona's (assistant) reply, sending it unmodified would make
  the evaluator continue the roleplay instead of returning the feedback JSON.
  This is a non-obvious, easy-to-accidentally-break API constraint discovered
  during this milestone's final review. **Do not remove this trailing message.**
- `extract_evaluation(response_body) -> dict`: parses the JSON response,
  including defensive handling for markdown fence formatting (`\`\`\`json
  {...}\`\`\``). Returns only the six validated fields (whitelisting defense):
  dimensions (with only the four specified keys), overall_summary, and
  improvement_recommendations. Any extraneous field (even a stray numeric one)
  is not passed through, preventing API surprises.
- `get_evaluation(messages, persona, session) -> dict`: makes the real
  Bedrock call and returns the extracted result.

**Frontend route** (`POST /evaluate`): required `session` (unlike `/chat`'s
optional session); returns 400 if persona_id is unknown (matching `/chat`'s
pattern), 503 on any Bedrock/parsing failure.

**Frontend UI** (`static/index.html`):
- `#get-feedback-btn`: shown/hidden with the roleplay setup form, disabled
  when no conversation yet or while a request is in flight. Reads `conversation`
  and `roleplaySession` (both already in scope from existing chat code) and
  POSTs to `/evaluate`.
- `#feedback-panel`: a results panel showing the four dimension assessments,
  overall summary, and recommendations as plain text. Toggled via
  `style.display` (not the `hidden` attribute), matching the existing
  inline-style pattern already load-bearing for `#chat`/`#chat-form`. On
  failure, shows a single error message; `conversation` and `roleplaySession`
  are never touched, so the user can immediately retry, keep chatting, or
  start a new roleplay. The existing "New Roleplay" button hides this panel
  on reset so stale feedback doesn't linger on screen.

See `docs/superpowers/specs/2026-09-18-performance-feedback-design.md` for
the full source-grounding rationale, why every dimension is included,
what's deliberately excluded, and manual QA acceptance criteria.

**Manually verified end-to-end in Chrome by the user** (2026-09-18):
Performance Feedback works correctly — evaluation generates qualitative-only
feedback with all six required fields for all three personas (Dr. Sarah Chen,
Dr. Marcus Reyes, Dr. Priya Nair) — and shows no regressions: Text Chat
works normally in the same session after feedback is shown; Live Voice works
across multiple consecutive turns before and after using Get Feedback; the
Simli avatar connects/animates/lip-syncs correctly; ElevenLabs audio plays
correctly; audio-unlock works; the feedback panel is correctly hidden when
"New Roleplay" is clicked, leaving the conversation fully reset; no session
leakage or data corruption observed.

## Therapeutic Area / Product Knowledge (Reference Material)

A Roleplay Session can carry one optional free-text `reference_material`
field — product / therapeutic-area facts the user pastes at setup — that
grounds both the persona's replies and the Performance Feedback
evaluation. It is client-held and sent whole on every `/chat` and
`/evaluate` call, exactly like `scenario`/`objective`/`mood`. Nothing is
stored, retrieved, indexed, uploaded, or parsed: **no RAG, embeddings,
vector store, document ingestion, or Admin/content management**.

**Source basis, and what this is not.** The Strategy doc's "Therapeutic
Area Knowledge Base" (Core Feature #2; "Single therapeutic area knowledge
base" in the V1.0 MVP list) is stated as an *outcome*, never a mechanism;
RAG/vector stores/upload appear only under Echo Admin. This slice delivers
the *effect* (a conversation and evaluation grounded in supplied facts),
not the *asset* (a curated, persisted, MLR-approved, admin-managed
knowledge base). The material is unverified and exactly as "approved" as
the user makes it; "FDA label-bound responses" is not enforced. See
`docs/superpowers/specs/2026-09-18-therapeutic-area-knowledge-design.md`
(source-backed requirements S1–S6 vs. implementation decisions D1–D11) and
its plan in `docs/superpowers/plans/`.

**Contract** (`app/main.py`): `RoleplaySessionRequest.reference_material:
str | None`, `Field(max_length=REFERENCE_MATERIAL_MAX_CHARS)` with the
constant `8000` — a Mini ECHO guardrail, **not a source requirement**. The
textarea's `maxlength="8000"` and hint text mirror it by hand (a build-free
frontend has no shared constant — change all of them together). Over-cap
or wrong-typed values are a 422 before any Bedrock call. Both `/chat` and
`/evaluate` call `request.session.model_dump(exclude_none=True)`; this is
load-bearing — without it the session dict handed to `get_reply`/
`get_evaluation` gains `reference_material: None` and breaks the
exact-dict assertions in `tests/test_main.py`.

**Persona prompt** (`app/bedrock.py`): `REFERENCE_MATERIAL_FRAMING` plus a
`<reference_material>…</reference_material>` block, inserted after the
difficulty line and **before** `persona.safety_framing` (which must stay
the last text of the prompt). The persona treats the material as ground
truth without reciting or volunteering it (it plays the HCP, not the rep),
pushes back on claims that contradict it, and asks for data on claims it
doesn't cover instead of inventing clinical facts.

**Evaluation prompt** (`app/evaluation.py`): its own
`REFERENCE_MATERIAL_FRAMING`, inserted between the "Evaluate only the
user's turns…" sentence and the JSON-format instructions. The evaluator
judges `message_accuracy`/`compliance_adherence` only against the material:
contradictions are called out, claims beyond it are "cannot be verified
from the material" (not "wrong"), the persona's own statements are not
evidence, and it does not vouch for the material. The no-numbers rule is
narrowed **only when material is present**: the evaluator may quote or
discuss figures that appear in the material, but must never introduce a
number that isn't in it or use numbers to score, weight, rank, threshold,
grade, or certify. This is prompt-only — `extract_evaluation` enforces
nothing numeric. The two modules keep separate copies of the framing and
the one-line normalization on purpose (different roles; `evaluation.py`
still imports only `MODEL_ID`/`REGION` from `bedrock.py`).

**Empty preserves behavior exactly.** Absent, `null`, `""`, and
whitespace-only values yield prompts byte-identical to the pre-milestone
ones. Verified by comparing the old (`6498290`) and new builders across
every persona × difficulty × scenario × empty-value form (108 combinations,
prompts and full request bodies), plus tests; the frontend also omits the
key entirely when the trimmed textarea is empty, so request payloads are
unchanged too.

**Frontend** (`static/index.html`): a labeled textarea
`#reference-material-input` and a live character counter
`#reference-material-count` (browser `maxlength` truncates silently, so the
counter makes the limit visible) sit in the setup form after Difficulty.
The submit handler adds `reference_material` to `roleplaySession` only when
the trimmed value is non-empty. The textarea keeps its text across "New
Roleplay", like the other setup inputs. The change is CSS + additive markup
+ three small script additions; `avatar-src/`, `static/dist/`, and
`static/stt-web-speech.js` are untouched and no `npm run build` was needed.

**Known limitations (accepted):** 8,000 characters fits a key-facts sheet,
not a full prescribing-information document; the material is resent with
every turn (a little extra token cost/latency); pasted text goes to AWS
Bedrock like the rest of the conversation; no indicator shows during a
session that material is active; the text between the tags is not
sanitized (the author is the sole consumer of their own session); the model
may still ignore or misapply the material — prompt behavior is confirmed
by manual QA, not guaranteed by tests. 19 automated tests cover the
contract, cap, prompt content/ordering, and empty-value equality.

**Manually verified in Chrome by the user** (2026-09-18): the user ran the
manual QA checklist from the design spec (grounded persona behavior,
evaluation content, blank-field behavior, Text Chat and Live Voice, all
three personas, counter and cap, New Roleplay, layout, and the
avatar/audio/feedback regression checks) and reported that it passed and
everything works as expected. No per-item breakdown was recorded beyond
that. This is a confirmed working feature, part of the stable baseline.

## ElevenLabs TTS integration (`app/tts.py`)

- `synthesize_speech(text, voice_id=DEFAULT_VOICE_ID) -> bytes`: POSTs to
  `https://api.elevenlabs.io/v1/text-to-speech/{voice_id}?output_format=pcm_16000`,
  returns the raw response body (PCM16, 16kHz — exactly what Simli's
  `sendAudioData` expects, verified: no format conversion needed anywhere).
- `list_voices() -> list[dict]`: GETs `https://api.elevenlabs.io/v2/voices`,
  returns just `[{"voice_id", "name"}, ...]`.

## Current working avatar/audio/WebRTC flow (end to end)

1. Page loads → `DoctorAvatar.connect()` runs immediately (before any user
   interaction) → `POST /avatar/session` → Simli session token → `SimliClient`
   (livekit transport) connects → video track attaches to `#avatar-video` and
   starts rendering (state → `"idle"` once the first frame actually renders, not
   merely once the connection handshake completes).
2. User types a message, submits the form → `avatar.think()` (state →
   `"thinking"`) → `POST /chat` (full conversation history) → Bedrock reply text
   appended to the chat log.
3. `avatar.speak(replyText, selectedVoiceId)` → `POST /tts` → PCM16 audio bytes →
   `client.sendAudioData(...)` → Simli's server renders synced video AND emits a
   `"speaking"` event (state → `"speaking"`, glow/equalizer animate) → when Simli
   finishes, emits `"silent"` (state → `"idle"`).
4. Audio is heard through the `#avatar-audio` element, which Simli's LiveKit
   transport attaches the incoming audio track to directly — the frontend never
   builds its own audio graph or a second audio path.

## Important fixes made (do not re-break these)

1. **Chrome audio-autoplay block.** The `<video>` has no audio track (silent
   video autoplays fine everywhere); the separate `<audio>` element's *first*
   `play()` — fired automatically by the SDK the instant the remote audio track
   arrives, before any user gesture — is rejected by Chrome
   (`NotAllowedError: play() failed because the user didn't interact...`).
   Fixed in `DoctorAvatar._setupAudioUnlock()`: a one-time listener on `click` /
   `keydown` / `touchstart` on `document` that retries `this.audioEl.play()` once
   a real gesture occurs. It does **not** create or resume any `AudioContext`
   (there is an internal, unused one inside `simli-client` for microphone capture
   we never use — that warning is benign and out of our control). Handled with
   `.then()/.catch()`, never an unhandled rejection.
2. **Avatar rendering invisible despite a working stream.** The poster `<img>`
   and `<video>` were stacked in normal document flow (no `position: absolute`)
   inside a wrapper with `overflow: hidden` and a fixed aspect ratio — the video,
   coming second in the DOM, was pushed almost entirely outside the visible
   clipped area even though it was genuinely receiving and rendering frames. Also,
   a `display: block` rule on the video had high enough CSS specificity to
   silently override the `hidden` attribute's own `display: none`. Fixed by (a)
   giving both `img` and `video` inside `#avatar-video-wrap` `position: absolute;
   top:0; left:0` so they properly overlap, and (b) driving the show/hide toggle
   via `element.style.display` (inline styles always win) instead of the `hidden`
   attribute, in the `playing` event handler in `static/index.html`.
3. **`livekit` transport mode, not `p2p`.** `p2p` requires fetching ICE servers
   (another API-key-bearing call we'd have to proxy server-side); `livekit` mode
   needs `iceServers: null` and just works through Simli's own relay. Established
   by reading `simli-client`'s actual TypeScript source, not docs (docs were
   incomplete/ambiguous on this point).

## Important architectural decisions

- **Backend stays stateless.** The browser holds the full conversation array and
  sends it whole on every `/chat` call. No database, no server-side session
  store, ever (this was a decision from the original MVP and still holds).
- **Provider abstraction for the avatar.** `app/avatar_provider.py` defines the
  interface; `app/avatar_simli.py` is the only Simli-specific file. Swapping
  avatar vendors later means writing one new file implementing the same
  interface and changing one import in `app/main.py` — not a rewrite.
- **TTS is isolated from the avatar provider**, in its own file
  (`app/tts.py`) with its own two functions. This was validated in practice: the
  Polly→ElevenLabs swap (forced by the AWS SCP block) touched only this file.
- **All third-party API keys stay server-side.** The browser only ever receives
  short-lived, scoped values (a Simli session token, raw TTS audio bytes) — never
  a raw API key. Verify this holds for any new integration too.
- **The frontend build step is scoped as narrowly as possible.** Only
  `avatar-src/doctor-avatar.js` goes through esbuild, because Simli's SDK leaves
  no alternative. Everything else in `static/index.html` is deliberately
  build-free plain HTML/CSS/JS — don't expand the build step to cover more of the
  page without a real reason forcing it, the way Simli's SDK forced this one.
- **Visual/CSS changes are kept surgically separate from functional/JS changes**
  whenever possible (see the cinematic redesign commit) — when asked for a purely
  visual change, prefer touching only CSS/markup and verify the `<script>` blocks
  are untouched by diffing, not just eyeballing.

## Things that MUST NOT be broken or unnecessarily rewritten

- The exact DOM contract `DoctorAvatar` and the inline script depend on:
  - IDs: `#chat`, `#chat-form`, `#message-input`, a `<button>` inside the form,
    `#avatar-template` (containing one `<img class="avatar">`), `#voice-select`,
    `#avatar-video` (must be a real `<video>`), `#avatar-audio` (must be a real
    `<audio>`), `#avatar-poster`, `#avatar-panel`, `#avatar-state-badge`
  - Classes set dynamically by `addMessage()` and relied on by CSS: `.message`
    plus exactly one of `.user` / `.ai` / `.error`, and `.bubble` — these are
    generated by string concatenation in JS (`'message ' + sender`), so CSS must
    target these exact class names, nothing else is available to style on them
  - The `DoctorAvatar` constructor's expected shape:
    `{ videoEl, audioEl, panelEl, stateEl }`
  - The five states `DoctorAvatar` itself emits, and nothing invented beyond
    them there: `connecting`, `idle`, `thinking`, `speaking`, `error`. A 6th
    state, `listening`, exists at the page level (set by the voice
    controller in `static/index.html`, never by `DoctorAvatar`) — see "Live
    Voice Conversation integration" above.
- The `position: absolute` overlay + inline-style-toggle fix for the video/poster
  (regressing to `hidden`-attribute-only toggling or removing the absolute
  positioning reintroduces the "invisible video" bug)
- `#chat` and `form#chat-form`'s inline `style="display: ..."` toggling (not
  the `hidden` attribute) — both have an explicit CSS `display: flex` rule at
  id-level specificity that would silently override `hidden`. Originally the
  video/poster bug's fix pattern; now also load-bearing for the roleplay
  setup flow gating the chat UI (see "Roleplay Sessions").
- The audio-unlock gesture listener (removing it reintroduces the Chrome autoplay
  bug)
- `"livekit"` as the Simli transport mode (switching to `"p2p"` requires adding
  ICE server fetching that doesn't currently exist)
- The stateless backend — do not add server-side conversation storage without an
  explicit decision to do so
- `scripts/bedrock_check.py` — frozen on purpose, do not "fix" its divergence
  from `app/bedrock.py`
- Never put a Simli or ElevenLabs (or any future provider's) API key in
  frontend code or expose it via an API response
- The trailing synthetic user message in `app/evaluation.py`'s
  `build_evaluation_request_body` — the final `{"role": "user",
  "content": "Now produce the evaluation JSON object described above."}` —
  is required to prevent Bedrock from continuing the roleplay instead of
  returning the evaluation JSON. The Anthropic Messages API treats
  assistant-final messages as a "prefill" for continuing that message;
  this trailing user turn makes the evaluator a fresh completion instead.
  Removing it reintroduces the role-confusion bug. Do not remove.
- Reference Material invariants: (a) `persona.safety_framing` must remain
  the last text of the persona system prompt — the reference block goes
  before it; (b) `model_dump(exclude_none=True)` at both `/chat` and
  `/evaluate` call sites in `app/main.py`; (c) an empty/whitespace/absent
  `reference_material` must leave both prompts byte-identical to the
  no-material version; (d) the evaluator's figure-quoting allowance applies
  only when material is present and never permits invented numbers or
  numeric scoring. See "Therapeutic Area / Product Knowledge" above.
